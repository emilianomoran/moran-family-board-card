# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — native Lit scoped CSS and Home Assistant theme variables |
| Preset | not applicable |
| Component library | none — Lit templates plus Home Assistant-provided elements |
| Icon library | Home Assistant `ha-icon` with Material Design Icons |

This is an existing Lit custom element, not a React, Next.js, or Vite application. The shadcn initialization gate is not applicable. Phase 1 must use the current component and theme patterns rather than introduce a parallel UI framework.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps and tightly related inline content |
| sm | 8px | Compact control gaps and event internals |
| md | 16px | Default control gaps and calendar-cell padding |
| lg | 24px | Wall header and toolbar horizontal padding |
| xl | 32px | Major layout separation within the header |
| 2xl | 48px | Minimum primary touch target and compact row height |
| 3xl | 64px | Toolbar bands and major vertical separation |

Exceptions: none. One-pixel dividers and the 10px, 12px, and 16px corner radii are visual treatments, not spacing values. Every wall-mode button or button-like target must be at least 48×48px.

---

## Typography

Wall mode uses exactly four sizes and two weights. Do not add intermediate type sizes or weights in the Phase 1 shell.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / event metadata | 14px | 400 | 1.5 |
| Label / control / event title | 16px | 700 | 1.25 |
| Heading / day context | 20px | 700 | 1.2 |
| Display / board title | 28px | 700 | 1.1 |

Times and dates use tabular numerals. Truncation may shorten secondary metadata, but visible event titles, person names or initials, and navigation labels must not be replaced by color or icon alone.

Source: the approved ranges in `docs/MORAN_DESIGN_SPEC.md`, narrowed to the four-role contract required for this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` | Full canvas, schedule background, person-header background |
| Secondary (30%) | `#f6f8fb` | Segmented controls, quiet status areas, empty/error support surfaces |
| Accent (10%) | `#1296ed` | Selected Day/view state, current-date action, keyboard focus ring, loading indicator |
| Primary text | `#111827` | Titles, labels, event text |
| Secondary text | `#526071` | Times, metadata, inactive controls |
| Divider | `#dfe5ec` | One-pixel grid and structural separators |
| Current time | `#e84235` | Current-time line and its time label only |
| Destructive | `#e84235` | Reserved; Phase 1 adds no destructive action |

Accent reserved for: selected Day/view state, current-date action, keyboard focus ring, and loading indicator. It must not become a generic border, decorative wash, event-owner color, or large-area background.

Person and event colors remain configuration/data-driven. Every colored event retains a readable title and time; every person color retains a visible name or initials. Event tint must preserve readable dark text on the approved white canvas.

## Phase Boundary

The Phase 1 UI is one opt-in proof slice. It demonstrates that `layout: wall` can compose the existing day calendar into a calm, full-panel wall experience without changing the default card.

| In contract | Explicitly deferred |
|-------------|---------------------|
| Calendar-only wall canvas | 68/32 household-operations rail |
| Restrained board/calendar header | Tasks, lists, meals, shopping, dinner, and their navigation |
| Existing date and view navigation when functional | Final cross-view wall styling |
| Existing day calendar with generic data | Final person filters and Everyone control |
| Visible person identity, time axis, events, and current-time marker inherited from day view | Final now/next hierarchy and glanceability tuning |
| Deterministic wall and legacy harness scenarios | Tablet, portrait, weather, and screenshot automation |
| Existing loading, empty, and total-error fragments remain functional if reached | New failure-state models, fixtures, retry behavior, stale/partial states, recurrence, and mutation hardening |

No control for a deferred feature may appear as a placeholder, disabled affordance, or decorative icon. Phase 1 does not read or mutate live Home Assistant configuration.

## 1920×1080 Layout Contract

The primary and only acceptance viewport for Phase 1 is 1920×1080 landscape. The wall shell fills the available panel and must read as one calendar product, not a Lovelace grid of nested cards.

| Region | Contract |
|--------|----------|
| Root canvas | Fill 100% available width and at least 100% panel height; white background; no outer margin, raised-card shadow, rounded card silhouette, or secondary column |
| Wall header | 72px high with 24px horizontal padding; board/calendar identity at left and the existing view switcher at right when more than one view is enabled |
| Day toolbar | 56px high with 24px horizontal padding; localized day/date context at left and existing previous/current/next date controls at right |
| Day tabs | A separate 56px row only when the configured day-tab control is present; omit the row rather than leave empty space |
| Schedule region | Flex to consume all height below the header/toolbars; this region, not the entire card, is the vertical scroll container |
| Time axis | 72px fixed width with right-aligned 14px tabular labels |
| Person lanes | Equal-width flexible columns; at the four-person fixture, each lane is at least 240px wide |
| Person header | 80px high; centered initials/avatar plus visible name; sticky while the schedule region scrolls |
| All-day row | Omitted when empty; otherwise at least 48px high and aligned exactly with the time axis and person columns |
| Event block | 12px radius, 8px internal gap/padding, subtle existing shadow only; visible title and time remain the primary content |
| Structural dividers | One-pixel `#dfe5ec`; no decorative borders around the overall calendar canvas |

At 1920×1080, board title, active view, day/date context, date navigation, every fixture person header, and the current-time marker must be visible without horizontal clipping. The schedule body may scroll vertically for hours outside the visible window, while its person header and all-day row remain anchored.

There is no left navigation rail in this phase. With Calendar as the only product surface, a rail containing only Calendar would waste scan width and rails for Tasks, Lists, Meals, or Home would violate the phase boundary.

## Visual Hierarchy

1. The schedule canvas is the dominant visual object and receives all width below the header.
2. The board title establishes product identity; day/date context establishes temporal location.
3. Person names or initials, the shared time axis, event titles, and event times are the first scan path inside the calendar.
4. Selected navigation uses the blue accent. Unselected controls use secondary text on the subtle surface.
5. The red current-time line is the only high-salience non-event mark in the grid.

Use 10px radii for controls, 12px for event blocks, and 16px only for a large shell section if one is required. Avoid bento cards, gradients, glass effects, decorative metrics, and nested content panels. Event colors may be softly tinted, but the canvas remains predominantly white.

## Component Contract

| Component | Phase 1 behavior |
|-----------|------------------|
| Wall shell | New opt-in wrapper activated only by normalized `layout: wall`; owns full-canvas sizing and wall-scoped tokens |
| Board header | Shows configured title, falling back to `Family Board`; contains no household-operations or weather controls |
| View switcher | Reuses enabled existing views and hides itself when only Day is enabled; all visible options must remain functional |
| Day toolbar | Reuses localized day/date text and date navigation; current-date action uses the visible `Today` label where the shell provides a dedicated action |
| Day calendar | Composes the existing day renderer and event logic; Phase 1 may add wall-scoped layout wrappers and CSS but does not rewrite calendar behavior |
| Person header | Keeps visible initials/avatar and name; does not add the Phase 2 Everyone/person-filter surface |
| Inherited state fragments | Existing loading, empty, and total-error fragments may be placed inside the wall shell without redesign; Phase 1 adds no new recovery component or data-state model |
| Visual editor layout field | Adds one `Layout` select backed by the shared config definition; choosing Wall writes `layout: wall`, while choosing Default removes the key |
| Legacy card | Uses the existing root/card composition and selectors when `layout` is absent; no wall sizing, header, or token override leaks into it |

New wall-shell markup and styles should live in a focused module when practical. Existing renderer extraction is allowed only where needed to mount the wall shell without enlarging the main component further.

## Interaction Contract

### Activation and compatibility

- `layout: wall` is the only public opt-in for the new shell.
- Missing `layout` normalizes to the existing legacy/default presentation. Legacy title, enabled views, current view behavior, date navigation, event interactions, editor round-tripping, and unknown configuration keys remain unchanged.
- The generic wall harness starts in Day view. Other configured views may remain reachable through the existing switcher, but Phase 1 does not claim wall-layout completeness for them.
- The upstream and Moran custom-element names remain separate; the wall shell must not register or reclaim an upstream alias.

### Controls

- All wall-shell controls are native buttons or expose equivalent button/tab semantics.
- Every target is at least 48×48px and works with touch, pointer, Enter, and Space where applicable.
- Keyboard focus uses a 2px `#1296ed` outline with a 2px offset and is never removed without a visible replacement.
- View tabs expose `role="tab"` and `aria-selected`; date arrows use explicit accessible names.
- Hover may reinforce a control but never reveal a required action.
- Existing event open/create/edit/delete behavior is preserved rather than redesigned. Phase 1 adds no new mutation affordance or recurrence promise.

### Motion

- Wall-shell state transitions use 160ms ease-out.
- Under `prefers-reduced-motion: reduce`, nonessential transform, pulse, and transition effects are disabled. State changes remain immediate and visible.
- No entrance animation, carousel, auto-advancing content, or ambient motion is introduced.

### Deferred interactions

- Do not add the Everyone/person filter group, a new profile-filter bar, final now/next cards, weather interaction, operations navigation, or add-item controls.
- If person-header toggling or event dialogs are inherited from the existing day renderer, they may remain functional but receive no new Phase 1 feature treatment.

### Visual editor

- Add one `Layout` select to the existing editor using the exact option and help copy in the copywriting contract.
- `Default` represents an absent `layout` key; the editor must not write a new default value into legacy configurations.
- `Wall` writes exactly `layout: wall` and emits the editor's existing complete bubbling `config-changed` event.
- Switching either option preserves every recognized setting and every unknown legacy key during the editor round-trip.
- The editor does not add wall-specific household, weather, filter, or operations settings in Phase 1.

## State Contract

| State | Visual and interaction behavior |
|-------|---------------------------------|
| Wall ready | Full header, toolbar, person header, time axis, deterministic events, and current-time marker render inside one canvas |
| Legacy | Existing non-wall rendering remains visually and behaviorally unchanged when `layout` is absent |
| Inherited loading, empty, or total error | Preserve existing behavior and keep the wall shell mounted if these states occur; use the contracted copy if a touched fragment needs text, but do not add a new fixture, retry action, or visual-state system in Phase 1 |

Loading/empty/error redesign, partial failure, stale data, unsupported calendars, retry mechanics, and comprehensive failure recovery are Phase 4 contracts. Phase 1 must not imply that these states are solved, but its seams must not prevent them later.

## Deterministic Harness Contract

Two public, synthetic scenarios are required:

| Scenario | Configuration | Purpose |
|----------|---------------|---------|
| Legacy baseline | Existing representative config with no `layout` key | Prove unchanged defaults and behavior |
| Wall day | Equivalent calendar data plus `layout: wall`, starting in Day | Prove the full-panel shell and wall-scoped styling |

The wall-day scenario uses a fixed clock of Wednesday, February 18, 2026 at 3:32 PM in a fixed test timezone and a 1920×1080 viewport. It uses only generic fixture entities such as `calendar.fixture_family` and `calendar.fixture_activities`.

Use four generic lanes: Avery, Jordan, Casey, and Household. Synthetic events must include:

- one all-day event;
- ordinary timed events in multiple lanes;
- at least one overlap within a lane;
- one shared-calendar event routed to multiple named people;
- one unmatched event routed to Household;
- one event spanning the fixed current time so the current-time marker is visually testable.

Fixture date, time, locale/time preference, events, people, colors, entity IDs, and Home Assistant responses must be deterministic. No live family name, schedule, entity ID, address, credential, screenshot, or Home Assistant state may enter the fixture or evidence.
