# Walking Skeleton — Moran Family Board Card

**Phase:** 1
**Generated:** 2026-09-10
**Status:** Planned; proof is pending execution of Plans 01-01 through 01-03.

## Capability Proven End-to-End

> A Home Assistant administrator can opt into `layout: wall` and run a deterministic local Day view through the compiled custom card while an equivalent configuration without that key keeps the legacy presentation.

For this brownfield browser card, “end-to-end” means Lovelace-shaped config -> shared normalization -> authenticated Home Assistant-shaped calendar read -> existing event routing/model -> existing Day renderer -> opt-in wall shell -> compiled bundle in the loopback harness. It does not mean adding a server, database, calendar write, or live Home Assistant deployment.

## Architectural Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Implementation base | Continue this Moran fork; use `tienou/family-calendar-card` as a pinned source/design reference | The Moran fork already has tested person routing, the exact five-view vocabulary, strict TypeScript, and safer HA-only credentials. The ADR is the formal gate. |
| Framework | Existing TypeScript 5 + Lit 3 custom element | Preserves Home Assistant dashboard hosting, theme variables, lifecycle, and one small HACS bundle; no React application is needed. |
| Configuration | One `src/config.ts` raw/public contract plus pure normalization and lossless serialization | Exact `layout: wall` opts in while absent/unknown values and editor Default preserve legacy config. |
| Data layer | External calendars through a narrow typed `hass.callApi` adapter | Home Assistant already owns provider authentication and calendar access; no second data store or direct provider credential is allowed. |
| Auth | Home Assistant frontend session, supplied through `hass` | Authentication/session management is not implemented by this card and no credential is stored in config, source, or fixtures. |
| Routing | Existing custom-element entry and top-level layout render branch; URL routing is not applicable | The product is one Lovelace card, not a routed web application. Existing Day/Timeline/Week/Month/Agenda state stays inside the element. |
| Calendar domain | Preserve `src/events.ts` routing, parsing, segmentation, and overlap logic | This tested pure module is already the correct domain backbone and must not fork for wall mode. |
| Wall presentation | Focused `src/wall-shell.ts` receives existing templates and owns only wall-scoped layout/styles | Prevents the 3,800-line controller from absorbing the full new surface and protects legacy CSS. |
| Time | Non-dashboard injectable display clock with a system-clock default | Makes the local proof deterministic without persisting a test-only Lovelace key or globally replacing `Date`. |
| Persistence | Home Assistant Lovelace config and external calendars; no project database | A database read/write is intentionally N/A because adding one would violate the source-of-truth constraint. Phase 1 performs a real authenticated HA-shaped calendar read and no calendar mutation. |
| Deployment analog | Existing Rollup build plus loopback `dev/harness.html?scenario=legacy|wall` | Produces a real self-contained artifact and exercises the full browser path without touching a live dashboard. Live deployment is Phase 5. |
| Directory layout | Focused modules under `src/`, collocated `*.test.ts`, generic fixture under `dev/`, generated artifact under `dist/` | Matches repository conventions and gives later slices explicit seams rather than a rewrite. |

## Stack Touched in Phase 1

- [x] Project scaffold — inherited and retained: TypeScript, Lit, Rollup, Vitest, Prettier, Node 20 CI. No framework initialization or dependency install is required.
- [x] Routing — URL/application routing is N/A; the real custom-element entry and `layout` presentation branch are exercised.
- [x] Database — N/A by architecture and product constraint. Home Assistant/external calendars remain the data owners; the skeleton proves one real read through mocked authenticated `hass`, and Phase 1 intentionally performs no write.
- [ ] UI — execution must make `layout: wall` render the calendar-only full-panel Day shell and leave legacy unchanged.
- [ ] Deployment — execution must build `dist/moran-family-board-card.js` and document the complete loopback production-bundle run.

## Security and Privacy Contract

- The browser bundle is public and contains no token, private endpoint, Calendar Bridge credential, household event, or live entity identifier.
- All runtime reads use the supplied authenticated Home Assistant client.
- Event and person text is rendered with normal Lit interpolation; `unsafeHTML` and `innerHTML` are not part of the skeleton.
- Only exact `layout: wall` selects the new shell; every other value remains legacy.
- `dist/moran-family-board-card.js` is generated by Rollup from reviewed source and is never edited directly.
- No dependency is added in Phase 1; an unexpected package or lockfile change blocks the phase.

## Out of Scope (Deferred to Later Slices)

- Everyone/person filters, final now/next hierarchy, dense-day policy, and glanceability tuning.
- Finished wall treatment for Timeline, Week, Month, and Agenda.
- Weather completion, tablet landscape, portrait/mobile, and automated browser screenshots.
- New loading/empty/partial/stale/retry models, recurrence safety, or mutation redesign.
- Calendar Bridge, direct provider access, logistics, tasks, shopping, meals, chores, rewards, photos, and AI import.
- Any live Home Assistant dashboard/resource change or pilot.

## Subsequent Slice Plan

Each later phase adds a vertical calendar capability on top of these decisions without replacing the shared config, authenticated HA adapter, tested event domain, or opt-in shell boundary:

- Phase 2: Make the Day view family-at-a-glance with robust data normalization, person filters, shared ownership, and now/next focus.
- Phase 3: Carry the interaction language across Timeline, Week, Month, Agenda, tablet, portrait, and the status/weather header.
- Phase 4: Harden event actions, recurrence scope, accessibility, failure states, stale data, retry, and kiosk recovery.
- Phase 5: Add browser/visual automation, verify the HACS beta, and run the separately reviewed reversible Home Assistant pilot.
